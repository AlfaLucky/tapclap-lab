# Tapclap Lab

Панель запуска и наблюдения за браузерными проверками игры «Сокровища пиратов».
Единственный разрешённый стенд: https://gems2-testers.stand.tapclap.com/.

Это независимый инструмент QA, не продукт TAPCLAP. Приложение не содержит
демонстрационных «успешных» прогонов, чужих учётных данных или заранее придуманных багов.

## Что реализовано

| Возможность | Реализация |
| --- | --- |
| Запуск с сайта | Выбор отдельных smoke-тестов и визуальных сценариев, постановка в очередь |
| Окружение | Chromium / Firefox / WebKit; desktop 1280×720, mobile 390×844, tablet 820×1180 |
| Повторы | 1–10 повторов, максимум 60 проверок за прогон |
| Статусы | Живые события worker, текущий тест и шаг, индикатор выполнения |
| Скриншоты | Обновляемый кадр во время работы и отдельный PNG для каждого выполненного теста |
| Трансляция | Настоящий MJPEG-поток скриншотов браузера, по умолчанию 4 кадра/с, до 6 кадров/с |
| Записи | WebM после закрытия контекста теста, просмотр и перемотка в панели |
| Управление | Отмена ожидающего/активного прогона; повтор всего набора или только упавших проверок |
| История | SQLite, результаты и материалы после перезапуска, HTML-отчёт и ZIP |
| Диагностика | Необработанные JS-ошибки, console warnings/errors, ошибки загрузки ресурсов стенда, Playwright trace, JUnit XML |
| Сравнение | Сопоставление результатов и длительности двух прогонов |
| Стабильность | Pass rate без skipped, сочетания passed/failed, среднее время и график последних 20 измерений |
| Расписание | Ежедневные запуски с фиксированным смещением UTC, включение/пауза |
| Доступ | Публичный просмотр по умолчанию, сессионный вход администратора для всех изменений |
| Canvas | Создание шаблонов из реального кадра, варианты на каждый браузер/профиль, конструктор сценариев |
| Хранение | Удаление старых артефактов по сроку и бюджету; метаданные прогонов сохраняются |

«Трансляция» — низкочастотный поток реальных кадров, а не 30/60-fps видеострим
и не интерактивный удалённый рабочий стол. Произвольное ручное управление браузером
из публичной панели не предоставляется. Сценарии нажимают и перетаскивают элементы
по описанным шагам.

## Быстрый запуск на Railway Hobby

1. Загрузить **содержимое этой папки** в отдельный GitHub-репозиторий.
2. В Railway: New Project → Deploy from GitHub repo → выбрать репозиторий.
   Если папка вложена в другой репозиторий, задать Root Directory этой папкой.
   Railway использует Dockerfile и railway.json.
3. Создать **Volume с точкой монтирования `/data`** для сервиса.
4. В Variables добавить:

   ```dotenv
   ADMIN_TOKEN=<случайный ключ длиной от 24 символов>
   HOST=0.0.0.0
   DATA_DIR=/data
   COOKIE_SECURE=true
   PUBLIC_READ=true
   RETENTION_DAYS=7
   ARTIFACT_BUDGET_MB=1000
   MAX_RUN_SECONDS=1200
   LIVE_FPS=4
   ```

   Сгенерировать ключ локально:

   ```bash
   python3 -c "import secrets; print(secrets.token_urlsafe(32))"
   ```

   Не добавлять настоящий ключ в репозиторий. `PORT` Railway задаёт автоматически.
5. Оставить **одну реплику**. Для первого браузерного прогона ориентир — лимит
   памяти 2 GB и 1 vCPU; это начальная настройка, не измеренное потребление.
   После пробного запуска проверить фактическую память и затраты.
6. Generate Domain → открыть приложение → «Войти» → ввести `ADMIN_TOKEN`.
7. Запустить сначала только **HTTP** и **Canvas**, затем полный smoke-набор.
8. Для ежедневного расписания сервис должен оставаться включённым;
   отключить автоматическое засыпание, если оно включено в настройках сервиса.

Без Volume SQLite и материалы могут пропасть при новом развёртывании.
`$5` Hobby не означают неограниченную работу браузера: ресурсы расходуются вместе
с остальными проектами аккаунта. Начинать с одного короткого прогона и проверить
метрики Railway до включения частого расписания.

База не требует отдельного PostgreSQL/Redis. Приложение использует Python HTTP
server с потоками и SQLite; браузер работает в отдельном завершаемом процессе.
Это сознательно компактная архитектура для одного владельца и одного worker.
Она не предназначена для множества независимых команд и горизонтальных реплик.

## Локальный запуск

Для полного приложения: **Python 3.12**, доступ в Интернет и установленные
системные зависимости браузеров. Серверные модульные тесты работают и на Python 3.9.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m playwright install chromium firefox webkit

export ADMIN_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export COOKIE_SECURE=false
export DATA_DIR=./data
python -m lab.server
```

Открыть http://127.0.0.1:8080. Для входа использовать значение `ADMIN_TOKEN`
из своего терминала. На Linux вместо `playwright install` можно выполнить
`python -m playwright install --with-deps chromium firefox webkit`.

Docker:

```bash
docker build -t tapclap-lab .
docker run --rm -p 8080:8080 --shm-size=1g \
  -e ADMIN_TOKEN -e COOKIE_SECURE=false \
  -v tapclap-lab-data:/data tapclap-lab
```

## Визуальные сценарии для этой игры

Большая часть игры нарисована в `#gameCanvas`. Кнопки внутри него не становятся
HTML-элементами, поэтому `getByRole('button')` не сможет найти игровые кнопки.
Используется сопоставление изображений OpenCV.

1. Выбрать только «Калибровка: длительное наблюдение» и таймаут 90–180 секунд.
   Сеанс держит страницу открытой для сбора кадров, не проверяет игровые
   утверждения и поэтому завершается со статусом skipped. Не включать его
   в регулярный smoke-набор.
2. Вкладка «Калибровка Canvas» → «Захватить кадр». Также доступен последний кадр
   завершённого прогона, пока не истёк срок хранения.
3. Выделить уникальный устойчивый элемент готового игрового экрана. Сохранить
   под именем `game_ready`. **Не использовать загрузочную заставку как готовый экран.**
4. Сохранить шаблоны видимых игровых кнопок и ожидаемых окон: например,
   `settings_button`, `settings_window`. Имена — пример, сами кнопки здесь
   заранее не исследованы и не объявляются существующими.
5. Создать сценарий: ждать `game_ready` → нажать `settings_button` →
   проверить `settings_window`. Если нужна перезагрузка для проверки сохранения
   игровой настройки, добавить reload и assert ожидаемого состояния.
6. Сценарий появится в наборе проверок и сможет запускаться по расписанию.

В сценарии обязателен хотя бы один **assert**. Доступны wait, click, assert,
reload, screenshot, drag. Drag задаётся четырьмя числами от 0 до 1 относительно
всего viewport и выполняет перетаскивание мышью. На мобильном профиле click
использует touch, кроме Firefox. Полноценная проверка native Android/iOS и
реального touch drag требует отдельного устройства/исполнителя.

Шаблоны хранят варианты для каждой пары браузер/профиль, исходные пиксели
не растягиваются. Для другого окружения нужно сохранить соответствующий вариант.
Порог совпадения 0.96. Почти одноцветные шаблоны отклоняются исполнителем.
Несовпадение может быть следствием масштаба, локали, анимации или реального дефекта;
материалы нужно анализировать.

Для проверки эталона сохранить **полный кадр** с именем
`baseline_desktop_chromium` (или соответствующей парой profile/browser).
Проверка сначала ищет `game_ready`, затем сравнивает кадры:
допуск 5% изменённых пикселей, порог разницы канала 35/255.
Создаётся `*-diff.png`. Динамические области пока не маскируются;
на анимированном поле эту проверку следует применять только после стабилизации.

## Что означают готовые тесты

| ID | Что действительно проверяется |
| --- | --- |
| `http` | Успех загрузки главного HTTP-документа |
| `canvas` | Видимость и размеры Canvas, **не** готовность игры |
| `render` | Canvas не одноцветен; заставка тоже проходит эту проверку |
| `layout` | Canvas помещается в viewport, нет горизонтальной прокрутки |
| `reload` | Canvas появляется после reload, **не** сохранность игрового прогресса |
| `javascript` | Нет необработанных JS-ошибок за 12 секунд после появления Canvas |
| `resources` | Нет failed / HTTP 4xx–5xx к домену стенда за окно наблюдения |
| `ready` | Найден откалиброванный шаблон готового игрового экрана |
| `baseline` | Готовый экран сопоставлен с утверждённым эталоном |
| `observe` | Длительный сеанс захвата кадров для калибровки, не проверка; итог skipped |

Для уровня, победы, поражения, списания ходов и прогресса нужны сценарии
с реальными игровыми наблюдениями и ожидаемыми результатами. Они не подменяются
проверкой HTTP или наличия картинки. Без шаблонов ready/baseline получают
**skipped**. Если весь прогон пропущен, итог тоже **skipped**, а не passed.

При ошибке запуска браузера итог — **error**. При перезапуске сервиса активный
прогон — **interrupted**, очередь сохраняется. При отмене worker получает
кооперативную остановку, затем принудительно завершается группа процессов,
если он не закрылся. В последнем случае запись последнего теста может быть неполной.

## API и материалы

- `GET /api/catalog`, `/api/runs`, `/api/stats`, `/api/schedules` — просмотр.
- `POST /api/login` с `{"token":"..."}` — HttpOnly/SameSite сессия на 12 часов.
- `POST /api/runs` — запуск; поля browser, profile, tests, repeat, timeout.
- `POST /api/runs/{id}/cancel` — остановка.
- `POST /api/runs/{id}/retry` с `{"failed_only":true}` — повтор ошибок.
- `GET /api/runs/{id}/events?after=0` — инкрементальный журнал.
- `GET /api/runs/{id}/stream` — MJPEG; `/snapshot` — последний JPEG.
- `GET /api/runs/{id}/files` — список материалов.
- `GET /api/runs/{id}/artifacts/{relative-path}` — материалы, включая trace и журнал.
- `GET /api/runs/{id}/report`, `/download` — HTML и ZIP.
- `POST /api/templates`, `/api/scenarios`, `/api/schedules` — сохранение настроек.

CLI-клиенты могут использовать `Authorization: Bearer <ADMIN_TOKEN>`.
Ключ не хранится в JavaScript/localStorage и не нужен посетителям для просмотра.
`PUBLIC_READ=false` закрывает и просмотр API/материалов до входа.
Запуск с чужого Origin блокируется. URL тестирования фиксирован, произвольный
Python/JavaScript из интерфейса не выполняется.

ZIP содержит автономный HTML со ссылками на лежащие рядом скриншоты, JUnit,
браузерные журналы, видео и traces. Для открытия trace:

```bash
python -m playwright show-trace ./01-01-trace.zip
```

Максимум 6 одновременных MJPEG-подключений, очередь до 10 ожидающих прогонов,
общий таймаут по умолчанию 20 минут. ZIP ограничен 100 MB; большие материалы
скачивать по отдельности. Видеофайлы обслуживаются с поддержкой HTTP Range.

## Проверки самого приложения

```bash
python -m unittest discover -s tests -v
node --check lab/static/app.js
python -m compileall -q lab
```

Проверяются HTTP-маршруты, сессии и права, очередь, отмена процессов, восстановление,
расписание UTC+4, статистика, обработка ошибок worker, семантика smoke-проверок,
варианты шаблонов, skipped и защита путей материалов.
HTTP-тесты вызывают реальные обработчики с транспортом в памяти: сеть не нужна.
Тестовый subprocess используется только в tests/ и не поставляет данные панели.

В `.github/workflows/check.yml` эти проверки выполняются при push/PR.
В `.github/workflows/live-smoke.yml` — **ручной** реальный прогон стенда с
загрузкой материалов в GitHub Actions artifacts; по умолчанию он не запускается.

## Проверено в среде разработки

Серверные тесты и синтаксис JavaScript/Python проверены локально. Здесь были
недоступны DNS/внешняя сеть, открытие локального порта, зависимости Playwright
и запуск Chromium. Поэтому **сквозной прогон по игре, визуальная проверка
интерфейса в браузере и сборка Docker не выполнены**. Это конкретные оставшиеся
проверки после развёртывания, а не подтверждённые успешные результаты игры.
Подробности и результаты проверок: [VALIDATION.md](VALIDATION.md).
